# PaperForge 2.0.0 包体与遗留代码清理（2026-11-04）

> 结论：`arm64-v8a` 完整包的体积由**功能载荷**决定，不是由应用层代码或死资源决定。169 MB 中 89.4% 是 LibreOffice 原生库、ONNX/ORT 推理库与随包模型；可证伪的死资源只有 1 个许可证文本，可安全删除的死代码 103 行，对 APK 体积的影响在 2 KB 量级。因此本轮交付「有证据的小幅删除 + 不可删项的量化边界」，不为了数字牺牲 Office/扫描/OCR 能力。

## 3. 死资源 / 死代码盘点（只读）

### 3.1 方法

1. 解包 APK 1,714 个条目，按目录聚合（§2）。
2. 建立源码语料：`app/src`、`full-app/src`、`archive-core`、`office-engine`、`format-engine`、`network-engine`、`ocr-paddle`、`theme-core`、`jpeg2000`、`opencv-mobile` 下的 `.kt/.java/.cpp/.h/.xml/.kts/.json/.pro`，共 **663 个文件**；排除 `build/`、`.git/`、`.gradle/`、`.cxx/`。
3. 对 **6,397 个顶层声明**做词边界引用计数：同名出现次数等于声明次数 ⇒ 除声明外无人命名（`scan_dead2.py`）。
4. assets 逐个用「完整相对路径 / 文件名 / 配置键」在语料中查找（`scan_assets.py`）；文档目录 `docs/` 不计为引用，避免文档掩盖死代码。
5. 原生库按 ELF `DT_NEEDED` + Java 端 `System.loadLibrary` + 全 APK 字符串引用三重核对（`elf_deps.py`、`scan_strings.py`）。
6. 依赖用 `import` 计数核对（§3.5）。

### 3.2 assets：没有可删的死资源

- 对可由源码判定的 assets 分区（`retouch/`、`scan/`、`docquad/`、`fonts/`、`color/`、`templates/`、`lan/`、`archive/`、根文件）逐条用完整路径/文件名/配置键核对：**唯一零命中**是 `assets/templates/LICENSE-python-pptx.txt`（1,124 B）——**许可证文本，按规矩保留**。
- `share/`、`unpack/`、`program/`、`layout/`、`org/`、`com/`、`native/`、`dexopt/`、`mlkit-google-ocr-models/` 这些目录由 LibreOffice / PDFBox / ML Kit / JLaTeXMath 在运行期按路径或资源名读取，不能靠“源码里有没有这个字符串”判死；它们逐目录的体量与依据见 §2.3、§5.3。
- 大块资源全部有活引用：DocRes/DocQuad/超分/边界/去弯/ML Kit 模型、CJK 字体、PDFBox CMap 与 AFM、veraPDF 规则 XML、LO 注册表/预设/字体。逐项引用见 §2.3 与 §5。
- 一度疑似「旧模型」的 `assets/retouch/super-resolution-10.onnx`（240 KB）仍在 `RetouchModels.kt:81` 使用；`assets/retouch/models.json`（998 B）没有任何代码读取，但它只是模型来源登记表，删除无体积意义且损失来源记录，**保留**。

### 3.3 res：资源收缩已生效，未发现可再删的资源

- `full-app/build/outputs/mapping/release/resources.txt` 里 aapt2 判定未使用的依赖资源共 128 个（`abc_fade_*`、`abc_slide_*`、`abc_btn_colored_*` 等 appcompat 项），已由 `shrinkResources` 移除；APK 内只剩 375 个 res 条目、压缩后 969,547 B。
- 其中最大的 `res/8C.png`（805,060 B）用 `aapt2 dump resources` 反查为 `drawable/brand_logo_source`，4 处代码/布局引用，**保留**。
- 源码 `res/` 目录本身只有 1.33 MB（最大一项就是上述品牌图源文件），不存在“旧版本图片堆”。

### 3.4 代码：6,397 个声明里 26 个可疑，逐一人工复核后删 15 个

- 引用计数给出 26 个候选，人工核对后：
  - **15 个确证无引用、且不属于框架回调/覆写/反射** → 删除（§4）；
  - 4 个是 data class 属性（`ImageGeometry.DecodePlan.sourceLong/requestedLong`、`PageCopyResult.firstPosition`、`OCRResult.wordBoxes`），**保留**：删除会改变 `componentN` 顺序，破坏解构调用与序列化，静态分析无法证伪；
  - 4 个是公开 API 但对应已记录功能（`MainViewModel.openOutputInLibrary/extractText/officeResult`、`PdfTools.decrypt`），**保留并上报**（§5.4）；
  - 3 个是 vendored 上游文件里的成员（`ocr-paddle/.../BitmapUtils.bitmapToRGBMat`、`bgrMatToBitmap`、`OCRError.DecodeError`），**保留**：`ocr-paddle/UPSTREAM.md` 记录了上游提交与「保留原始文件头」的约束，删函数会削弱后续同步能力，而收益 < 200 B。
- 未做全量静态调用图分析：Kotlin/Compose 合成函数与 R8 keep 规则会让“图”失真；本轮用「词边界引用 + 编译 + 单测」三重证据，宁可少删不误删。

### 3.6 重复实现：存在历史分支，但都仍可达

- `IndependentDocumentDetector` / `IndependentPageDewarp`（2.2 KB / 2.5 KB）看似“旧实现”，实际由引擎选择分支 `if (engine == "INDEPENDENT")` 调用（`DocumentDetector.kt:163` 等），属于可选引擎，**保留**。
- `DocumentDetector`（边缘/几何）与 `LearnedDocumentDetector`（DocQuadNet）同时存在是**设计上的双通道**：`IndependentDocumentDetector.detect` 用一致性融合二者，不是残留。
- `ScanProcessor` / `EnhancePipeline` / `ScanRetouch` 都仍在扫描→增强→导出链路中被引用（引用数 130 / 14 / 16），不是可删分支。
- 结论：没有“旧版本开关导致的整段死路径”，本项目的“史山”更多是**未接线的小函数**（§4），不是整模块残留。
